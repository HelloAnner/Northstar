## 一、背景与核心目标

### 1.1 现状问题

001 版本已实现两条调整路径：

| 路径 | 入口 | 现状 |
|------|------|------|
| 手动调整 | 前端表格编辑 + 指标调整 | DAG 反向算法，固定权重逻辑硬编码 |
| AI 调整 | `/api/optimize` + `/api/llm/chat` | 各自独立逻辑，规则无法共享 |

**问题：** 两条路径的随机分配逻辑中没有外部可配置的规则参与，用户无法描述"某指标不能太高"这类约束，系统也无法在分配过程中自动规避违规结果。

### 1.2 目标

**引入统一规则驱动层 `role.json`**，规则直接参与随机分配算法，而非事后校验：

```
用户自然语言规则
      ↓ LLM 转换
   role.json（结构化约束）
      ↓ 加载为可执行 Constraint 对象
随机分配算法（Constraint 约束 target 裁剪 + 分配量限制 + 联动补偿）
      ↑              ↑
   手动调整       AI 调整（意图解析后走同一引擎）
```

**关键点：** role.json 的每条规则都会被转换为一段可执行的约束逻辑，嵌入 `ApplyIndicatorTarget` 的分配过程中，使调整结果天然符合规则，而不是调完再检查。

## 三、role.json 规则设计

### 3.1 设计原则

1. **规则即逻辑**：每条规则对应一类具体的算法干预行为，可直接映射为 Go 函数
2. **参与分配过程**：规则不是事后检查，而是在 `ApplyIndicatorTarget` 执行中实时生效
3. **指标 ID 对齐**：所有 indicator 字段与现有 16 项指标 ID 严格对应
4. **最小结构**：JSON 字段精简，每个字段对执行逻辑都有直接意义

### 3.2 规则类型（三种，覆盖主要场景）

| 类型 | 干预时机 | 说明 | 示例 |
|------|----------|------|------|
| `clamp_target` | 分配**前**，裁剪请求的目标值 | 防止非法或不合理目标进入分配 | 限上增速不超过 15% |
| `filter_allocation` | 分配**中**，过滤参与分配的企业集合 | 约束哪些企业参与此次调整 | 只调正增长企业 |
| `compensate` | 分配**后**，自动触发关联指标调整 | 维护跨指标关系 | 批发增速不低于零售 |

### 3.3 role.json Schema

```json
{
  "version": "1.0",
  "updatedAt": "2026-03-14T10:00:00Z",
  "sourceFile": "config/rules.md",
  "rules": [
    {
      "id": "rule_001",
      "name": "限上增速上限 15%",
      "description": "限上社零额当月增速不超过 15%",
      "type": "clamp_target",
      "indicator": "limitAbove_month_rate",
      "min": null,
      "max": 15.0
    },
    {
      "id": "rule_002",
      "name": "批发增速区间",
      "description": "批发业当月增速在 -10% 到 20% 之间",
      "type": "clamp_target",
      "indicator": "wholesale_month_rate",
      "min": -10.0,
      "max": 20.0
    },
    {
      "id": "rule_003",
      "name": "零售正增长过滤",
      "description": "调整零售增速时，仅分配给当前已是正增长的企业",
      "type": "filter_allocation",
      "indicator": "retail_month_rate",
      "filter": "positive_current"
    },
    {
      "id": "rule_004",
      "name": "批发补偿零售",
      "description": "调整零售增速后，若批发低于零售则自动向上补偿批发",
      "type": "compensate",
      "trigger": "retail_month_rate",
      "ensure": "wholesale_month_rate",
      "relation": "gte",
      "tolerance": 0.0
    }
  ]
}
```

### 3.4 indicator 枚举（与现有 16 项对齐）

```
limitAbove_month_value / limitAbove_month_rate
limitAbove_cumulative_value / limitAbove_cumulative_rate
eatWearUse_month_rate / microSmall_month_rate
wholesale_month_rate / wholesale_cumulative_rate
retail_month_rate / retail_cumulative_rate
accommodation_month_rate / accommodation_cumulative_rate
catering_month_rate / catering_cumulative_rate
totalSocial_cumulative_value / totalSocial_cumulative_rate
```

### 3.5 各类型字段说明

**`clamp_target`：**

| 字段 | 类型 | 说明 |
|------|------|------|
| `indicator` | string | 被裁剪的目标指标 |
| `min` | float64 \| null | 最小值，null 表示无限制 |
| `max` | float64 \| null | 最大值，null 表示无限制 |

**`filter_allocation`：**

| 字段 | 类型 | 说明 |
|------|------|------|
| `indicator` | string | 触发此规则的目标指标 |
| `filter` | string | 过滤模式，枚举值见下表 |

filter 枚举：

| 值 | 含义 |
|----|------|
| `positive_current` | 仅参与当前值 > 0 的企业 |
| `negative_current` | 仅参与当前值 < 0 的企业 |
| `large_scale_only` | 仅参与 company_scale=1（大型）企业 |
| `exclude_small_micro` | 排除小微企业 |

**`compensate`：**

| 字段 | 类型 | 说明 |
|------|------|------|
| `trigger` | string | 当此指标被调整时激活 |
| `ensure` | string | 自动补偿调整的目标指标 |
| `relation` | string | `gte`（ensure ≥ trigger）/ `lte`（ensure ≤ trigger） |
| `tolerance` | float64 | 允许偏差容忍量，0.0 表示严格 |

## 四、规则管理模块

### 4.1 用户规则 MD 格式

用户以自然语言列表的方式写入规则，存储为 `config/rules.md`：

```markdown
# 调整规则

1. 限上社零额当月增速不超过 15%
2. 批发业当月增速不低于 -10%，不高于 20%
3. 零售业增速应保持正增长
4. 批发增速不应低于零售增速
5. 社零总额累计增速不能太低，需在 3% 以上
```

**格式约束：**
- 编号列表，每行一条规则
- 纯自然语言，无需结构化
- 编辑后保存即触发自动转换

### 4.2 前端规则列表 UI

**路由：** `/settings/rules`（或集成到现有设置页）

**功能：**
- 列表展示所有规则（按编号排列）
- 新增规则：弹出对话框，输入自然语言文本
- 编辑规则：点击编辑图标，修改文本
- 删除规则：点击删除图标，确认后删除
- 保存后自动触发后台 MD → role.json 转换
- 显示 role.json 最后更新时间，以及转换状态（成功/失败/进行中）

**API：**

```
GET  /api/rules          → 返回规则列表（从 rules.md 解析）
POST /api/rules          → 新增一条规则
PUT  /api/rules/:index   → 编辑第 index 条规则
DELETE /api/rules/:index → 删除第 index 条规则
POST /api/rules/convert  → 手动触发 MD → role.json 转换（保存时自动调用）
GET  /api/rules/status   → 查询转换状态（updatedAt / lastError）
```

### 4.3 自动转换流程

```
用户保存规则
     ↓
写入 config/rules.md
     ↓
异步触发 LLM 转换任务
     ↓
LLM 读取 rules.md → 输出 role.json
     ↓
写入 config/role.json
     ↓
通知前端转换完成（状态 API polling 或 SSE）
```

### 4.4 转换详细设计

LLM 转换的完整设计见 **§7.1**（包含 System Prompt 全文、extractJSON 策略、校验逻辑、异步状态管理）。

## 五、系统提示词配置

### 5.1 两类提示词的分层设计

AI 对话模块使用两层提示词，职责严格分离：

| 层级 | 名称 | 是否可修改 | 作用 |
|------|------|----------|------|
| 内置层 | **内置规则提示词** | **不允许用户修改** | 描述系统背景、指标枚举、调整逻辑约束等，确保 AI 理解业务场景 |
| 用户层 | **偏好提示词** | 用户可配置 | 调整 AI 的输出风格、分析侧重点、回复语气等个性化偏好 |

运行时两层拼接方式：

```
[内置规则提示词（固定）]
---
[用户偏好提示词（可配置）]
```

## 六、AI 调整流程（统一引擎）

### 6.1 当前 AI 调整问题

- `/api/llm/chat` 目前是纯对话，AI 返回文本，无结构化执行
- `/api/optimize` 是手动触发的指标调整，不经过 AI

### 6.2 新的 AI 调整流程

```
用户对话："把限上增速调到 8%"
              ↓
     AI 理解意图，生成 AdjustmentPlan
     {
       "actions": [
         { "type": "set_indicator", "indicatorId": "limitAbove_month_rate", "value": 8.0 }
       ]
     }
              ↓
     后端验证 AdjustmentPlan 对 role.json 的合规性
     （检查是否违反 hard 规则）
              ↓
     执行调整（复用现有 ApplyIndicatorTarget + RecalcAll）
              ↓
     返回执行结果 + 规则检查报告（soft 规则是否触发）
              ↓
     AI 以自然语言描述调整结果和违规提示
```

```json
{
  "actions": [
    {
      "type": "set_indicator",

    }
  ]
}
```

## 七、三段链路详细设计：rules.md → role.json → 对象 → 调整驱动

### 7.0 三段链路总览

```
rules.md（自然语言）
     │
     │  ① LLM 转换（rules/converter.go）
     │     - 把中文描述转为结构化 JSON
     │     - 验证 indicator ID 合法性
     │     - 写入 config/role.json
     ▼
role.json（结构化规则文件）
     │
     │  ② JSON 解析（rules/loader.go）
     │     - 按 type 字段分发到对应 Constraint 类型
     │     - 构建 RuleSet，热重载
     ▼
RuleSet（Go 对象，内存中）
     │
     │  ③ 注入 ApplyIndicatorTarget（dagcalc/adjust.go）
     │     - 干预点1：ClampTarget（分配前）
     │     - 干预点2：FilterAllocation（分配中）
     │     - 干预点3：Compensate（分配后）
     ▼
调整结果符合规则

```

### 7.1 第一段：rules.md → role.json（LLM 转换）

#### 7.1.1 rules.md 格式规范

```markdown
# 调整规则

1. 限上社零额当月增速不超过 15%
2. 批发业当月增速不低于 -10%，不高于 20%
3. 调整零售增速时，仅分配给当前已是正增长的企业
4. 批发增速不应低于零售增速
5. 社零总额累计增速不能低于 3%
```

规则以有序列表写入，每行一条，纯自然语言，无格式要求。

#### 7.1.2 LLM 接入方式

复用现有 `internal/llm` 包（已封装 Claude API），新增 `converter.go`：

```go
// internal/rules/converter.go

type Converter struct {
    llm      llm.Client      // 复用现有 Claude 客户端
    rolePath string          // config/role.json
    store    store.Store     // 读写转换状态
}

// ConvertAsync 异步执行转换，立即返回
func (c *Converter) ConvertAsync(mdContent string) {
    go func() {
        c.store.SetConfig("rules_convert_status", "running")
        result, err := c.convert(mdContent)
        if err != nil {
            c.store.SetConfig("rules_convert_status", "error")
            c.store.SetConfig("rules_convert_error", err.Error())
            return
        }
        os.WriteFile(c.rolePath, []byte(result), 0644)
        c.store.SetConfig("rules_convert_status", "ok")
        c.store.SetConfig("rules_convert_at", time.Now().Format(time.RFC3339))
        engine.ReloadRules()  // 写入成功后热重载
    }()
}
```

#### 7.1.3 LLM 调用结构

使用 **单次非流式** 调用（不需要 stream，等待完整 JSON 输出）：

```go
func (c *Converter) convert(mdContent string) (string, error) {
    resp, err := c.llm.Chat(llm.ChatRequest{
        System: buildSystemPrompt(),
        Messages: []llm.Message{
            {Role: "user", Content: buildUserMessage(mdContent)},
        },
        MaxTokens: 2048,
    })
    if err != nil {
        return "", fmt.Errorf("LLM 调用失败: %w", err)
    }

    jsonStr, err := extractJSON(resp.Content)  // 从响应中提取 JSON 块
    if err != nil {
        return "", fmt.Errorf("提取 JSON 失败: %w", err)
    }

    if err := validateRoleJSON(jsonStr); err != nil {  // 结构校验
        return "", fmt.Errorf("JSON 校验失败: %w", err)
    }

    return jsonStr, nil
}
```

#### 7.1.4 System Prompt（完整）

```
你是一个结构化数据转换助手，专门将中文自然语言约束规则转换为 JSON 格式。

# 系统背景

Northstar 是月度经济数据统计系统，管理批发、零售、住宿、餐饮四大行业的 16 项指标。
用户以自然语言描述数据调整规则，你需要将其转换为可执行的 JSON 约束。

# 可用指标 ID（必须严格使用以下 ID，不能自创）

limitAbove_month_value      - 限上社零额（当月值）
limitAbove_month_rate       - 限上社零额增速（当月）
limitAbove_cumulative_value - 限上社零额（累计值）
limitAbove_cumulative_rate  - 限上社零额增速（累计）
eatWearUse_month_rate       - 吃穿用增速（当月）
microSmall_month_rate       - 小微企业增速（当月）
wholesale_month_rate        - 批发业销售额增速（当月）
wholesale_cumulative_rate   - 批发业销售额增速（累计）
retail_month_rate           - 零售业销售额增速（当月）
retail_cumulative_rate      - 零售业销售额增速（累计）
accommodation_month_rate    - 住宿业营业额增速（当月）
accommodation_cumulative_rate - 住宿业营业额增速（累计）
catering_month_rate         - 餐饮业营业额增速（当月）
catering_cumulative_rate    - 餐饮业营业额增速（累计）
totalSocial_cumulative_value - 社零总额（累计值）
totalSocial_cumulative_rate  - 社零总额增速（累计）

# 规则类型

## type: "clamp_target"
用途：限制调整时的目标值范围（如"不超过15%"、"不低于3%"）
必填字段：
  - indicator: 指标 ID（从上方枚举选）
  - min: 最小值（数字），无限制时为 null
  - max: 最大值（数字），无限制时为 null

## type: "filter_allocation"
用途：调整某指标时，限制参与随机分配的企业范围
必填字段：
  - indicator: 触发此规则的目标指标 ID
  - filter: 过滤模式（只能选以下值）
    * "positive_current"   - 只分配给当前值>0的企业
    * "negative_current"   - 只分配给当前值<0的企业
    * "large_scale_only"   - 只分配给大型企业（规模=大）
    * "exclude_small_micro" - 排除小微企业

## type: "compensate"
用途：调整某指标后，若关联指标关系被破坏，自动补偿
必填字段：
  - trigger: 触发补偿的指标 ID（被调整的指标）
  - ensure: 需要保持关系的指标 ID（被补偿的指标）
  - relation: "gte"（ensure >= trigger）或 "lte"（ensure <= trigger）
  - tolerance: 允许的容差（通常为 0.0）

# 输出格式

严格输出以下 JSON，不含任何解释文字、markdown 代码块标记：

{
  "version": "1.0",
  "rules": [
    {
      "id": "rule_001",
      "name": "规则简短名称",
      "description": "原始自然语言描述",
      "type": "...",
      ...对应类型的字段
    }
  ],
  "unrecognized": ["无法识别或映射的原始规则文本"]
}

id 从 rule_001 开始递增，unrecognized 在无不可识别规则时为空数组 []。
```

#### 7.1.6 extractJSON 策略

#### 7.1.7 validateRoleJSON 校验规则

```go
var validIndicators = map[string]bool{ /* 16 项 ID 全集 */ }
var validFilters    = map[string]bool{
    "positive_current": true, "negative_current": true,
    "large_scale_only": true, "exclude_small_micro": true,
}
var validRelations = map[string]bool{"gte": true, "lte": true}

// ValidationError 携带具体的错误描述，用于反馈给 LLM 重试
type ValidationError struct {
    RuleID  string
    Field   string
    Message string
}

func validateRoleJSON(jsonStr string) []ValidationError {
    var raw rawRoleJSON
    if err := json.Unmarshal([]byte(jsonStr), &raw); err != nil {
        return []ValidationError{{Message: "JSON 格式错误：" + err.Error()}}
    }
    var errs []ValidationError
    for _, r := range raw.Rules {
        switch r.Type {
        case "clamp_target":
            if !validIndicators[r.Indicator] {
                errs = append(errs, ValidationError{r.ID, "indicator",
                    fmt.Sprintf("%q 不在允许的指标 ID 列表中", r.Indicator)})
            }
            if r.Min == nil && r.Max == nil {
                errs = append(errs, ValidationError{r.ID, "min/max",
                    "min 和 max 不能同时为 null"})
            }
        case "filter_allocation":
            if !validIndicators[r.Indicator] {
                errs = append(errs, ValidationError{r.ID, "indicator",
                    fmt.Sprintf("%q 不在允许的指标 ID 列表中", r.Indicator)})
            }
            if !validFilters[r.Filter] {
                errs = append(errs, ValidationError{r.ID, "filter",
                    fmt.Sprintf("%q 不在允许的 filter 枚举中", r.Filter)})
            }
        case "compensate":
            if !validIndicators[r.Trigger] {
                errs = append(errs, ValidationError{r.ID, "trigger",
                    fmt.Sprintf("%q 不在允许的指标 ID 列表中", r.Trigger)})
            }
            if !validIndicators[r.Ensure] {
                errs = append(errs, ValidationError{r.ID, "ensure",
                    fmt.Sprintf("%q 不在允许的指标 ID 列表中", r.Ensure)})
            }
            if !validRelations[r.Relation] {
                errs = append(errs, ValidationError{r.ID, "relation",
                    "relation 必须为 gte 或 lte"})
            }
        default:
            errs = append(errs, ValidationError{r.ID, "type",
                fmt.Sprintf("未知规则类型 %q", r.Type)})
        }
    }
    return errs
}
```

#### 7.1.8 验证失败的多轮重试机制

转换不是"一次失败直接报错"，而是带错误反馈的多轮对话，最多重试 **3 次**：

```go
func (c *Converter) convert(mdContent string) (string, error) {
    messages := []llm.Message{
        {Role: "user", Content: buildUserMessage(mdContent)},
    }

    for attempt := 1; attempt <= 3; attempt++ {
        resp, err := c.llm.Chat(llm.ChatRequest{
            System:    buildSystemPrompt(),  // 内置规则提示词（不变）
            Messages:  messages,
            MaxTokens: 2048,
        })
        if err != nil {
            return "", fmt.Errorf("第%d次调用 LLM 失败: %w", attempt, err)
        }

        jsonStr, err := extractJSON(resp.Content)
        if err != nil {
            // 提取失败：追加错误上下文让 LLM 重试
            messages = append(messages,
                llm.Message{Role: "assistant", Content: resp.Content},
                llm.Message{Role: "user", Content: fmt.Sprintf(
                    "你的输出无法提取为 JSON，请只输出纯 JSON，不含任何解释文字。错误：%s", err)},
            )
            continue
        }

        errs := validateRoleJSON(jsonStr)
        if len(errs) == 0 {
            return jsonStr, nil  // 校验通过，返回
        }

        // 校验失败：把具体错误描述追加到对话，让 LLM 修正
        errMsg := buildValidationErrorMessage(errs)
        messages = append(messages,
            llm.Message{Role: "assistant", Content: resp.Content},
            llm.Message{Role: "user", Content: errMsg},
        )
    }

    return "", fmt.Errorf("经过 3 次尝试仍无法生成合法的 role.json，请检查规则描述是否清晰")
}

func buildValidationErrorMessage(errs []ValidationError) string {
    var sb strings.Builder
    sb.WriteString("生成的 JSON 存在以下问题，请修正后重新输出完整 JSON：\n\n")
    for _, e := range errs {
        if e.RuleID != "" {
            sb.WriteString(fmt.Sprintf("- 规则 %s 的字段 %s：%s\n", e.RuleID, e.Field, e.Message))
        } else {
            sb.WriteString(fmt.Sprintf("- %s\n", e.Message))
        }
    }
    sb.WriteString("\n请修正以上问题，只输出完整的合法 JSON，不含解释文字。")
    return sb.String()
}
```

**失败处理：**
- 3 次重试仍失败 → 保留上一次成功的 role.json，状态置为 `error`
- 错误信息存入 `rules_convert_error`（含最后一次验证错误详情）
- 前端在规则列表页展示错误详情，提示用户修改规则描述后重试

```go
// Load 读取 role.json，返回 RuleSet
func Load(path string) (*RuleSet, error) {
    data, err := os.ReadFile(path)
    // ... 处理文件不存在：返回空 RuleSet，不报错

    var raw rawRoleJSON
    json.Unmarshal(data, &raw)

    rs := &RuleSet{}
    for _, r := range raw.Rules {
        switch r.Type {
        case "clamp_target":
            rs.Clamps = append(rs.Clamps, &ClampTargetConstraint{
                ID: r.ID, IndicatorID: r.Indicator,
                Min: r.Min, Max: r.Max,
```

### 7.3 第三段：RuleSet → 调整驱动（执行机制）

#### 7.3.1 Constraint 类型定义

```go
// internal/rules/constraint.go

// ClampTargetConstraint：分配前裁剪目标值
type ClampTargetConstraint struct {
    ID          string
    IndicatorID string
    Min         *float64 // nil = 无下限
    Max         *float64 // nil = 无上限
}

func (c *ClampTargetConstraint) Clamp(indicatorID string, target float64) (float64, bool) {
    if c.IndicatorID != indicatorID {
        return target, false
    }
    orig := target
    if c.Max != nil && target > *c.Max { target = *c.Max }
    if c.Min != nil && target < *c.Min { target = *c.Min }
    return target, target != orig
}

// FilterAllocationConstraint：分配中过滤企业集合
type FilterAllocationConstraint struct {
    ID          string
    IndicatorID string
    Filter      string
}

func (c *FilterAllocationConstraint) Apply(indicatorID string, companies []CompanyRow) ([]CompanyRow, bool) {
    if c.IndicatorID != indicatorID {
        return companies, false
    }
    filtered := filterByMode(companies, c.Filter)
    return filtered, len(filtered) != len(companies)
}

// CompensateConstraint：分配后自动补偿关联指标
type CompensateConstraint struct {
    ID        string
    TriggerID string
    EnsureID  string
    Relation  string  // "gte" | "lte"
    Tolerance float64
}

// Check 返回是否需要补偿以及补偿的目标值
func (c *CompensateConstraint) Check(triggerID string, indicators map[string]float64) (bool, float64) {
    if c.TriggerID != triggerID {
        return false, 0
    }
    triggerVal := indicators[c.TriggerID]
    ensureVal  := indicators[c.EnsureID]
    switch c.Relation {
    case "gte":
        if ensureVal < triggerVal-c.Tolerance {
            return true, triggerVal - c.Tolerance
        }
    case "lte":
        if ensureVal > triggerVal+c.Tolerance {
            return true, triggerVal + c.Tolerance
        }
    }
    return false, 0
}
```

#### 7.3.3 filterByMode 实现（internal/rules/filter.go）

```go
func filterByMode(companies []CompanyRow, mode string) []CompanyRow {
    switch mode {
    case "positive_current":
        // 仅保留当前月增速 > 0 的企业
        return filter(companies, func(c CompanyRow) bool { return c.CurrentMonthRate > 0 })
    case "negative_current":
        return filter(companies, func(c CompanyRow) bool { return c.CurrentMonthRate < 0 })
    case "large_scale_only":
        return filter(companies, func(c CompanyRow) bool { return c.CompanyScale == 1 })
    case "exclude_small_micro":
        return filter(companies, func(c CompanyRow) bool { return !c.IsSmallMicro })
    default:
        return companies  // 未知 mode 不过滤
    }
}
```

## 十一、关键约束与边界

1. **提示词分层不可混用**：内置规则提示词硬编码，用户偏好提示词仅影响回复风格，二者不可互换
2. **转换多轮重试降级**：3 次失败后保留旧 role.json，调整引擎不中断
3. **规则作用于指标层**：三种 Constraint 均以 indicatorID 为粒度，不下沉到企业字段
4. **Compensate 防循环**：`depth` 参数控制，depth>0 时不再触发 Compensate，避免 A↔B 无限互调
5. **FilterAllocation 降级**：过滤后企业为空时回退全量企业，确保调整不失败
6. **AI 调整复用现有引擎**：不新建独立 AI 计算路径，全部走 `ApplyIndicatorTarget + RecalcAll`
7. **LLM 转换幂等**：相同 rules.md 多次触发应产生语义等价的 role.json
